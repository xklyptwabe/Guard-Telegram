# External operation outbox (BOTS-9)

External calls — the Telegram Bot API (moderation actions), S3 (`PutObject`), RabbitMQ (publish) — can fail in ways a normal database transaction can't paper over: the process can crash mid-call, the network can drop the response after the external system already applied the change, or the call can take longer than we're willing to wait. `moderation.pending_operations` (`src/db/schema/moderation.ts`) and `PendingOperationsOutbox` (`src/lib/moderation/pendingOperationsOutbox.ts`) exist to make these calls reliable and their outcome auditable, without ever claiming to know something we don't.

This is a distinct concern from `audit.outbox` (BOTS-6/7), which delivers an *already-recorded* audit event onward to a destination. `moderation.pending_operations` exists to make the *external call itself* reliable, before any audit event exists.

Operation kinds are namespaced — `telegram.*` (registered by `ModerationService`), `s3.putObject` (`lib/storage.ts`), `rabbitmq.publish` (`lib/rabbitmq.ts`) — one table, one worker, one terminal-audit pipeline for all of them (BOTS-9 review BLOCKER-3).

## Contract

1. **Write-ahead.** Before any external call, a row is inserted with `status = 'pending'` and a caller-supplied `idempotencyKey`, plus `request_payload` (exactly what gets sent) and a versioned `metadata` envelope. The envelope keeps policy-projected audit metadata separate from the minimal recovery identity needed by the finalizer after restart; a BOTS-8 allowlist or masking rule therefore cannot make an already-executed operation unauditable. Recovery fields are restricted to the typed actor/target/action/integration identifiers and still pass `stripForbidden`; optional data such as moderation reasons stays only in the policy-projected section. Legacy flat rows remain readable. If a row for the key already exists, it is looked up instead of inserted again. Files/bodies are never stored — S3 rows keep a digest, not the bytes.
2. **Claim (lease-based).** A row is never acted on just because its `status` reads `in_progress` — every attempt first atomically claims it by setting `worker_id` + `lease_expires_at` (`SELECT ... FOR UPDATE SKIP LOCKED` for the polling path, a conditional `UPDATE` for a directly-known row). A row left `in_progress` by a crashed worker is only reclaimable once its lease has genuinely expired.
3. **Resolve.**
   - A **confirmed** response — success, a `GrammyError`, or a `ConfirmedExternalError` (a non-Telegram provider that answered with its own rejection, e.g. an S3 4xx/5xx) — is terminal: `succeeded` or `failed`. `failed` is never retried; retrying an authoritative rejection (missing rights, access denied, …) would just fail again.
   - Anything else — a timeout, a network error, any unconfirmed exception — means **we do not know** whether the change was applied. The row goes to `unknown` with `next_attempt_at` scheduled for an exponential-backoff retry, up to `PENDING_OPERATION_MAX_ATTEMPTS` (`src/constants.ts`). A non-final `unknown` is not claimable before its backoff elapses, and an **exhausted** `unknown` (`next_attempt_at` NULL) is never blindly re-executed. If the process dies while a non-retryable operation is `in_progress`, recovery converts the expired lease directly to terminal `unknown` without calling the provider again. Re-running a possibly-already-applied, non-idempotent side effect without reconciliation is exactly what the BOTS-9 review forbids.
4. **Recover + retry.** `recoverPending()` runs once at startup (after `bot.init()`, before the transport accepts traffic) and then continuously via `startWorker()` — a persistent poll loop (`PENDING_OPERATION_WORKER_POLL_INTERVAL_MS`) for the whole process uptime, stopped in graceful shutdown (BOTS-9 review BLOCKER-2). Recovery re-attempts rows using a resolver registered by `kind`, so a fresh process can finish another process's work; `ModerationService` and the integration clients register their resolvers eagerly for exactly that.
5. **Durable audit finalization.** Every terminal outcome runs the finalizer once: it writes the one-and-only audit record (`moderation.action` / `message.deleted` for `telegram.*`, `integration.action` for `s3.*`/`rabbitmq.*`) keyed by the row's stable `${idempotencyKey}:audit`, then flips `audit_status` to `written`. If the audit write fails, `audit_status` stays `pending` and the worker's backfill pass retries **the audit only** — never the executor. The DB retains request, recovery metadata and provider result for as long as that debt exists; the same transition to `written` (or deliberate `policy_skipped`) atomically clears those JSON payloads and leaves the stable row identity/status as the dedup tombstone. The runtime role still cannot update payload columns directly.

## Compound operations: `kick`

`kick` is Telegram's own two-call idiom (ban, then immediately unban) — the Bot API has no atomic single-call primitive for it. It is modeled as **one** `pending_operations` row whose executor performs both calls, not two independent rows. This is a deliberate fix, not the original design: with two separate rows, a crash between "ban succeeded" and "the unban row gets written" left nothing on disk saying an unban was still owed, so recovery had no way to know to finish the job — the target would stay banned forever. With one row, a crash anywhere inside the executor just leaves that single row `in_progress`/`unknown`, and recovery re-invokes the *whole* executor. Both Telegram calls are individually idempotent (banning an already-banned user, or unbanning with `only_if_banned`, are no-ops), so replaying the pair from the top is always safe.

The one thing this doesn't paper over: a **confirmed** rejection on the unban half after the ban half already succeeded. That's terminal by design — a confirmed failure is never retried — so it can leave the target banned rather than kicked. The audit record says so explicitly (`partialOutcome: 'banned_not_kicked'`, BOTS-9 review HIGH-8) rather than presenting an indistinguishable generic failure; an operator needs to look at it, same as any other confirmed failure.

## Provider specifics (BOTS-9 review BLOCKER-3)

- **S3 `PutObject`** — the body is never written ahead (files are forbidden in the outbox). A live call executes with the caller's body in scope; recovery can't re-upload, so it *reconciles*: a successful `HEAD` proves the object exists (→ `succeeded`, recorded as reconciled). A `HEAD 404` only proves that the object is not visible at that instant: the timed-out `PUT` may still be completing, and a configured S3-compatible endpoint is not guaranteed to have AWS S3's exact consistency contract. It therefore remains `unknown` and is retried until the attempt limit; exhausted reconciliation remains terminal `unknown`, never a fabricated confirmed failure. `HEAD` is read-only, so retrying it is safe.
- **RabbitMQ publish** — the envelope, including its id, is created *before* write-ahead and stored in `request_payload`; every retry republishes the same envelope id, making consumer-side dedup possible. Publish failures are unconfirmed from this side and stay `unknown`, retried with the identical envelope.
- **RabbitMQ DLQ/retry rerouting** gets a post-call `integration.action` record but deliberately no write-ahead row: the source message stays unacked until the reroute is confirmed and is nacked back to the original queue on failure — RabbitMQ's own redelivery is the durable retry, and a DB roundtrip inside that ack window would change consumer ordering for no reliability gain.

## Documented exclusions (BOTS-9 review HIGH-5)

These external mutations are deliberately **not** routed through the outbox; each exclusion is marked at its call site in code:

- `sendMessage` / replies and `answerCallbackQuery` — user-facing UX feedback whose value decays in seconds; a post-restart retry would deliver stale responses, which is worse than a rare lost reply. The command outcome and its `command.executed` audit are independent of reply delivery.
- `setMyCommands` / `setWebhook` — bootstrap-only, idempotent, inherently retried by the next restart (retry-by-restart).
- RabbitMQ `ack` / `nack` — protocol-level acknowledgements; see the rerouting note above.
- Redis cache-aside writes — reproducible from the PostgreSQL source of truth; a missed fill self-heals on the next read.

## Telegram-update inbox (BOTS-9 review BLOCKER-5)

The *inbound* counterpart lives in `core.processed_updates` (`src/core/updateInbox.ts`): a `received → processing → completed` state machine, with `failed` awaiting redelivery under backoff. Only a `completed` row deduplicates; a crash or handler failure mid-processing leaves the row non-completed and Telegram's own redelivery reprocesses it. The raw update is never stored (BLOCKER-4), so redelivery is the retry driver; attempts are bounded by `INBOX_MAX_ATTEMPTS`, and retention purges only `completed` rows.

## One final audit record

`каждая операция создаёт одну итоговую запись` (each operation creates exactly one final record): the finalizer runs for exactly the terminal outcomes — confirmed `succeeded`/`failed` immediately, an `unknown` once (and only once) its retries are exhausted. An interim `unknown` is never audited; the next attempt's outcome is the one that counts. The write-ahead row itself is the redelivery idempotency: a redelivered Telegram Update producing the same `idempotencyKey` finds the existing row and returns its outcome without invoking the executor again.

A row resolving during recovery has no live command, actor, or Update on the call stack — everything needed to reconstruct the audit record (actor, target, action, reason, or the integration's identity fields) is written ahead into `pending_operations.metadata`, deliberately kept separate from `request_payload`. A row somehow missing that metadata is logged and skipped rather than guessed at.

## Residual, documented risk

`withTimeout` races the external call against our own clock; over plain HTTP it cannot cancel the in-flight request. If that request completes *after* the row already went `unknown` and a retry re-issued the call, safety depends on the operation's own idempotency — true for ban/unban/restrict and for RabbitMQ's stable envelope id, not provable for `deleteMessage` (a second delete of an already-deleted message returns a confirmed error, misreporting a succeeded delete as `failed`). Full reconciliation for that one case is a known, explicit gap, not a silently accepted one.
